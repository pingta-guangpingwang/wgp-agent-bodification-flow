## 摘要

当代智能体已经具备模型推理、工具调用、记忆、沙箱、审批、子智能体、运行环境和外部连接等复杂结构。随着代码生成能力普及，人类的工程杠杆正从"编写实现"转向"指定、组合与验证"：真正需要长期维护的产物变成了**装配配方**（由哪些组件、以什么配置、如何连接构成一台智能体）、**评测集**（什么叫更好）和**策略**（什么动作需要人负责）。

源代码拥有四十年积累的差分、评审、测试、归因与回滚工具链。智能体配置几乎什么都没有：它通常散落在配置文件、环境变量与界面开关中，改动没有语义差分，效果没有对照实验，退化没有责任定位。

WGP-ABF 提出一种平台无关的方法，把智能体配置转换为可解构、可编辑、可组装、可运行、可评估、可诊断的工程对象。其核心是三份协议与一份纪律：**结构协议**（WGP-ABIR 统一中间表示与拆解保真度分级）、**运行协议**（带持久性契约的运行事件）、**证据协议**（三级评测、双重评分与诊断报告最小字段）；纪律是二维工程图纸作为唯一结构事实源。人形机体与三维视图是可选的呈现投影，服务于沟通、教学与巡检，不参与结构定义与诊断定位。

> **一句话定义** WGP-ABF 让智能体配置成为可以画出来、比对、测量、换件并验证的工程对象。

**明确的非目标**：WGP-ABF 的价值主张**不是**"你不必再编写配置"。生成式模型已经消除了"手写慢"这个痛点，以编辑便利为卖点的可视化工具在今天最缺乏竞争力。WGP-ABF 交付的是**理解与归因**：看清一份配置实际做了什么，定位它哪一处薄弱，并验证一次改动是否真的构成改进。

# 第一部分 问题与定位

## 1. 背景与问题定义

智能体产品正在从单次问答演进为长期运行的软件系统。成熟智能体不再只有一个大模型，而是由上下文加载、工具选择、外部执行、会话状态、权限边界、记忆、验证与恢复共同构成。Claude Code 官方文档把核心循环描述为接收提示、评估、调用工具、获取结果并重复，直到返回最终结果；Codex 官方明确区分应用拥有的界面、业务上下文与授权控制，以及由 agent harness 承担的循环、会话、工具交互和沙箱执行；OpenClaw 进一步公开了 agent core、运行循环、会话、资源加载、工具策略、模型提供商与插件 harness 等边界。[1][2][4]

这些体系证明智能体内部已经形成相对稳定的工程部件。但用户面临七个共同问题：

- **结构不可见**：用户知道智能体"能做什么"，却无法一眼看清它"由什么组成"。
- **关系不可见**：数据、控制、依赖、权限和包含关系常被混在一张无类型节点图中。
- **运行不可见**：多数界面展示文字日志，却没有把真实事件投射回结构。
- **平台不可比**：不同框架术语、配置与扩展机制不同，难以用一套视图拆解和比较。
- **强弱不可见**：结果变差时，用户往往只能反复修改整个智能体，无法定位薄弱零件。
- **改装缺乏证据**：更换模型、工具或插件之后，缺少同任务、同环境的前后对比。
- **变更不可审查**：配置改动没有语义差分、没有风险标记、没有评审记录、没有可靠回滚。

前六项属于"看不清"，第七项属于"管不住"。两者共同的根因是同一个：**智能体配置已经成为主要工程产物，却仍被当作附属设置对待。**

> **问题判断** WGP-ABF 关注的不是"再做一个工作流编辑器"，也不是"再做一个链路追踪面板"，而是为智能体配置建立工程图纸、装配规则、运行证据与诊断进化系统。

## 2. 与现有工具体系的关系

WGP-ABF 不试图取代已有工具，而是补上它们共同缺失的那一层。判断依据是各类工具的**第一对象**——它们的数据模型以什么为中心。

| 工具类别 | 第一对象 | 解决什么 | 缺什么 |
|---|---|---|---|
| 轨迹与评测平台 | run 与 span | 这次运行发生了什么；这批任务分数多少 | 没有组件的结构性身份，因此无法回答"哪个可替换零件不行"，也没有换件与再验证闭环 |
| 节点式编排器 | 流程节点 | 编排的编写与部署 | 关系无类型（一根线表示一切）；权限与沙箱不是一等对象；无零件级评测；其"不用写代码"的价值主张正被生成式模型抵消 |
| 遥测规范 | 事件与属性 | 跨系统的事件归一化 | 不提供结构表示、装配语义与评测证据模型 |
| 配置管理与版本控制 | 文本文件与提交 | 变更留痕与回滚 | 差分是文本级的，不理解组件、端口、权限与依赖的语义 |

由此得到 WGP-ABF 的可防守位置，是上述四类的交集而非并集：

> **组件的结构性身份 + 语义化换件 + 同任务集复测。**
> 即：让智能体配置成为有差分、有测试、有归因的工程对象。

遥测规范是 WGP-ABF 观测层可以直接采纳的底座[8]；版本控制是配方的持久化去处（第 11 章）。WGP-ABF 只增加它们不覆盖的三份协议。

## 3. 概念与边界

WGP-ABF 是一种跨平台方法，用统一的结构协议、运行协议与证据协议，把既有或新建智能体转换为可解构、可编辑、可组装、可运行、可评估、可诊断的工程对象。它包含五个层次，其中前三层是必需的，第四层是可选的呈现。

| 层次 | 定义 | 主要产物 | 地位 |
|---|---|---|---|
| 逻辑层 | 智能体真实能力、状态和接口 | 组件、模块、关系、策略 | 必需 |
| 图纸层 | 逻辑层的二维可编辑投影 | WGP Blueprint、AssemblyRecipe、RecipeDiff | 必需，唯一事实源 |
| 观测评测层 | 真实运行数据与证据 | 运行事件、Trace、指标、评分、诊断 | 必需 |
| 机体投影层 | 结构的具象视觉投影 | 人形机体、二维零件、三维机甲 | 可选，只读 |

WGP-ABF 不是物理机器人标准，也不把具身智能与软件智能体混为一谈。"身体、器官、手臂、大脑"等词属于呈现层的认知翻译工具，其使用规则与失效边界由第 17 章约束。

WGP-ABF 也不把所有内容强行变成同一种节点。视觉外壳可以统一，底层必须区分资源、能力、流程、容器和治理对象，以避免数据文件、模型、权限策略与执行器被错误地赋予相同运行语义。

## 4. 核心原则

**结构与事实源**

1. **结构优先**：结构定义先于视觉表现；没有统一中间表示，就没有可信的二维或三维视图。
2. **二维为事实源**：所有编辑、接口校验、关系修改和版本记录，均在二维图纸或其底层数据中完成。
3. **投影只读**：机体视图与三维视图只读取同一份结构事实，不保存第二套业务模型。
4. **递归组合**：组件可组成模块，模块可组成机体，完整机体还能作为组件进入更大系统。
5. **平台中立**：差异由适配器吸收；ABIR 不绑定模型厂商、IDE、操作系统或通信渠道。

**隐喻纪律**

6. **隐喻不进类型系统**：机体词汇只出现在呈现层。ABIR 的类型名、诊断的定位层级、事件与指标的命名，一律使用工程名词（组件、边、容器、配方、事件、指标）。人体映射是渲染，不是定义。
7. **一个器官一种语义**：呈现层内部保持长期一致的映射；映射发生冲突时以工程结构为准，允许该对象在机体视图中显示为通用模块或不显示。

**证据纪律**

8. **真实事件驱动**：数据流、发光、动作和报错必须由真实运行事件驱动，不得用预设动画冒充执行。
9. **事件必须声明持久性**：每个运行事件必须标明它是持久、派生还是仅实时；回放与审计只能建立在持久事件上。
10. **结构必须声明来源与保真度**：每个组件、边、容器必须记录其结构来源等级；推断出的结构不得与声明读出的结构在视觉上无差别地混同。
11. **评分必须可追溯**：所有分数必须绑定任务集、环境、版本、权重、样本量、方差与原始证据，不产生无来源的综合分。
12. **诊断必须可行动**：诊断不只指出"哪里差"，还要指向具体的 componentId 或 edgeId、可执行的修复差分与验证计划。

**治理纪律**

13. **安全边界可见**：权限、沙箱、凭据、审批与危险操作必须成为一等组件和一等关系。
14. **图纸是特权产物**：完整的结构加权限视图是敏感资产，默认不对被诊断的智能体本身开放。
15. **改动必须可审查、可回滚**：任何装配变更必须能表达为可读的语义差分，并携带反向差分。
16. **可回放可审计**：任何一次运行都应能按时间轴重建关键事件、状态变化与产物来源。

> **工程底线** 二维图纸必须准确表达并真实影响运行；若图纸上的一次改动不能改变实际运行行为，该实现只是视觉演示。

## 5. 术语与层级

| 术语 | 规范定义 | 示例 |
|---|---|---|
| 组件 Component | 具有独立职责、明确输入输出和可观测生命周期的最小逻辑单元 | 模型路由器、文件工具、审批器 |
| 模块 Module | 由多个组件与内部关系构成的可复用子图 | 研究模块、编程模块、发布模块 |
| 整机 Agent Body | 能够接收任务并完成闭环运行的完整系统 | DSH 型机体、Codex 型机体 |
| 装配配方 Recipe | 组件实例、连接、参数、策略和布局提示的版本化集合 | 标准编码机体配方 v3 |
| 配方差分 Recipe Diff | 两份配方之间的语义差异，含风险标记与反向差分 | 换模型、开启网络出口、加装插件 |
| 插件 Plugin Mod | 通过标准插槽对已有组件或模块进行局部能力改装 | 网页检索插件、代码审查插件 |
| 运行轨迹 Trace | 一次运行产生的有序事件、状态变化、调用结果与产物引用 | 工具调用、审批、重试、完成 |
| 评测证据 Eval Evidence | 评分对应的任务、输入、输出、指标和环境记录 | 基准任务集、成本与耗时 |
| 诊断 Diagnosis | 从整机症状回溯到组件、边或配置的可验证结论 | 记忆检索低命中、工具权限阻断 |
| 零件 Body Part | 组件或模块在**呈现层**的具象表达 | 大脑、机械臂、记忆核心 |

**组件资格判定**：一个对象应当成为组件，须同时满足四条——可以独立替换、拥有明确输入输出、具有自身配置或状态、能够单独观察和测试。否则它更适合作为组件参数。例如模型温度是参数；模型路由器能够独立接收任务并输出模型选择，因此是组件。

注意"零件"一词的位置变化：它是呈现层术语，不是结构层术语。结构层只有组件、模块、容器、边。

## 6. 九阶段工作流

1. **智能体导入与拆解**：接入运行接口、项目目录或配置清单，建立可识别对象范围，并**同时判定拆解保真度**（第 8 章）。
2. **模块显形**：识别决策、执行、记忆、感知、治理、环境和输出等大模块。
3. **组件显形**：展开模块，识别模型、提示词、工具、记忆、审批、会话和执行器等原子组件。
4. **关系显形**：抽取包含、依赖、数据、控制、权限、引用和部署关系，并执行类型校验。
5. **二维图纸生成**：把拆解结果标准化为 ABIR，生成可编辑、可版本化的二维工程图纸。
6. **装配与改装**：按端口与插槽进行连接、类型验证、依赖检查、适配器推荐与插件挂载。
7. **差分与审查**：把改动表达为语义差分，标记风险，必要时进入人工批准，并生成反向差分。
8. **编译与运行**：把配方编译成目标平台可真实运行的配置，通电运行，用真实事件驱动高亮与时间轴。
9. **评测、诊断与再验证**：产出三级评分与诊断结论，用同任务集 A/B 验证改动，合格者记入版本历史。

> **过程体验** 同一个画布应支持逐步播放、暂停、人工修正、保存快照和回退。用户看到的不是九个割裂页面，而是一台智能体从不可见到被拆开、画出、改装、装回并通电验证的连续过程。

与 v0.2 相比，"组件零件化"从主流程移出（归入第 17 章的可选呈现），新增"差分与审查"为独立阶段。

# 第二部分 结构核心

## 7. WGP-ABIR 统一中间表示

WGP Agent Body Intermediate Representation（WGP-ABIR）是结构核心。所有适配器先转换为 ABIR，二维图纸、运行观测、评测证据与可选的机体视图再从 ABIR 生成。坐标只是视图属性，不能成为业务关系的唯一依据。

| 核心对象 | 职责 | 最低字段 |
|---|---|---|
| ComponentDefinition | 定义可复用组件类型 | type、version、ports、slots、capabilities、lifecycle |
| ComponentInstance | 记录项目中的组件实例 | id、definitionRef、config、state、**source**、**fidelity**、visualBinding |
| Edge | 表达组件之间的关系 | source、target、kind、schema、policy、**fidelity** |
| Container | 表达模块与递归包含 | id、children、exposedPorts、boundary |
| AssemblyRecipe | 描述整机装配方式 | instances、edges、policies、layoutHints、**recipeVersion** |
| **RecipeDiff** | 表达两份配方之间的语义变更 | base、target、changes、riskFlags、approval、rollback |
| RuntimeBinding | 绑定真实运行实体 | adapter、adapterVersion、runtimeId、sessionRef、capabilityMap |
| RuntimeEvent | 记录运行过程 | eventId、runId、time、componentId、type、status、**durability** |
| ArtifactRef | 引用运行产物 | uri、mediaType、hash、producer、provenance |
| PluginBinding | 表达插件对组件或模块的改装关系 | pluginRef、targetSlot、effects、permissions、rollback |
| MetricObservation | 记录某一时刻或测试的原始指标 | metricId、value、unit、scope、evidenceRef |
| EvaluationReport | 聚合零件、装配或整机评测结果 | level、profile、scores、**sampleSize**、**variance**、confidence、baseline |
| DiagnosisReport | 关联症状、根因、证据和可行动修复 | symptom、**suspectComponents**、**suspectEdges**、rootCause、evidence、actions、risk |

加粗字段为 v0.3 新增或强化。

组件实例示例：

```json
{
  "componentInstance": {
    "id": "tool.web.01",
    "definitionRef": "capability.tool.web@1.0.0",
    "source": "declared:profile.web/row#tool-web",
    "fidelity": "F3",
    "config": { "search": true, "fetch": false },
    "ports": {
      "inputs": [{ "name": "request", "schema": "web.request" }],
      "outputs": [{ "name": "result", "schema": "web.result" }]
    },
    "permissions": ["network.domain"],
    "visualBinding": { "part": "arm.browser", "lod": "module" }
  }
}
```

ABIR 应支持 JSON、YAML 或其他可验证序列化格式。规范层只要求语义一致，不要求所有实现使用相同存储。

## 8. 拆解保真度分级

自动拆解的准确率是这类方法能否成立的关键变量。v0.3 不把它留作开放问题，而是把结构来源变成一等属性，并规定不同等级允许的操作。

| 等级 | 名称 | 结构来源 | 允许的操作 |
|---|---|---|---|
| **F3** | 声明级 Declared | 直接读自平台自身的声明式配置或注册表，组件身份、配置字段与依赖边与运行实体一一对应 | 查看、编辑、换件、编译回运行配置、参与贡献归因 |
| **F2** | 内省级 Introspected | 通过平台提供的只读接口枚举实际加载的实体；身份可靠，字段可能不完整 | 查看、受限编辑、受限换件（仅限接口已确认的字段） |
| **F1** | 观测级 Observed | 只能从运行事件反推组件存在与调用关系，身份靠启发式聚合 | 仅查看与观测；不得作为换件或编译依据 |
| **F0** | 标注级 Asserted | 人工声明或文档推断，无运行证据 | 仅用于占位、教学与设计草图 |

**规则**

- 图纸必须逐对象显示保真度，且 F1/F0 对象在视觉上必须与 F3/F2 明显区分（例如虚化轮廓加标记）。
- 换件、编译回运行配置、以及"当前机体贡献分"只允许在 F3/F2 对象上进行。
- 一台机体的整体保真度取其关键路径上的最低等级。
- 跨平台比较必须标注双方保真度；**不同保真度的分数不得直接比较大小**，只能在同等级内比较，或明确标注差异后作定性参考。
- 适配器必须声明自己能达到的最高等级，并对每一类对象分别说明，不得整体宣称。

这一分级同时解决三个问题：把"拆解准不准"变成可申报、可核对的属性；防止推断结构被误当作可编辑事实；给跨平台比较设定合法边界。它也解释了参考实现的选择顺序（第 21 章）——不同平台的起步等级本来就不同。

## 9. 关系模型与可视化语法

关系必须是强类型对象，不能只是一根无语义的线。包围盒只表达包含关系，虚线只表达非运行依赖；两者不可互换，否则拆解结果会产生歧义。

| 关系类型 | 二维表现 | 运行语义 |
|---|---|---|
| data | 发光实线与方向粒子 | 数据包或流正在传输 |
| control | 细箭头 | 触发、分支、调用或控制顺序 |
| dependency | 默认隐藏的灰色虚线 | 版本、服务、环境或能力依赖 |
| containment | 半透明包围盒 | 组件属于模块或机体 |
| permission | 锁形端口或金色连线 | 权限、凭据或人工批准 |
| reference | 点划线 | 只读引用，不发生运行时拥有关系 |
| errorPropagation | 红色脉冲路径 | 错误、阻塞或降级传播 |

默认视图只显示关键数据和控制关系。选择组件、悬停、进入诊断模式或发生异常时，才揭示局部依赖。全量依赖必须通过 X-Ray 模式查看，以避免大型项目形成不可阅读的"蜘蛛网"。

## 10. 二维工程图纸

二维工程图纸是第一目标，也是全部结构编辑的主工作区。它同时承担拆解、设计、组装、调试与回放。

| 二维模式 | 主要任务 | 默认显示 |
|---|---|---|
| 解构模式 | 从整机逐层查看模块、组件和配置 | 包围盒、组件树、类型、版本、保真度 |
| 装配模式 | 拖拽、吸附、连接、适配和封装 | 端口、插槽、兼容性与缺失依赖 |
| 差分模式 | 审查一次装配改动 | 新增/删除/替换、配置字段变化、风险标记 |
| 运行模式 | 观察真实执行过程 | 数据流、调用状态、耗时和产物 |
| 诊断模式 | 定位错误、权限与性能问题 | 依赖、错误传播、瓶颈和审批阻塞 |

画布采用语义缩放：远距离只显示整机与大模块，中距离显示模块边界和关键端口，近距离显示原子组件、参数、数据契约和事件。任意子图都可以一键封装为模块，并暴露稳定接口供其他配方复用。

> **二维优先** 第一版无需实现三维编辑。只要二维能够真实拆解、装配、差分、运行和回放，方法论的工程价值即已成立。

## 11. 配置差分与变更审查

既然装配配方是主要工程产物，它就必须获得源代码级别的变更工程。这是 v0.3 新增的核心机制。

**语义差分，而非文本差分。** RecipeDiff 必须以工程对象为单位表达变更：新增/删除/替换的组件实例、变化的配置字段、变化的边、变化的容器边界、变化的权限关系、变化的插件绑定。文本级 diff 无法回答"这次改动是否放宽了沙箱"。

**风险标记必须显式。** 以下变更类别必须在差分中被标出，不得只体现为一行普通字段变化：

| 风险类别 | 触发条件 |
|---|---|
| 权限扩大 | 新增或放宽 permission 关系、提升凭据范围 |
| 网络出口引入 | 新增可访问外部网络的组件或域名范围 |
| 副作用引入 | 新增可写文件、执行命令、发布或调用外部可变状态的组件 |
| 审批绕过 | 移除审批组件、或把需审批动作改为自动 |
| 沙箱放宽 | 扩大文件、网络或进程边界 |
| 成本量级变化 | 预算、模型档位、并发或重试策略导致成本量级变动 |
| 保真度下降 | 引入 F1/F0 对象进入关键路径 |

**审批与责任。** 对具有副作用、成本显著或权限扩大的变更，系统必须要求人工批准，不得仅依据综合分自动换件。批准记录必须与差分绑定，形成责任归属。

**回滚是差分的一部分。** 每个 RecipeDiff 必须携带可执行的反向差分；不能生成反向差分的改动应被标记为不可逆并单独审批。

**与版本控制协作，而非取代它。** 配方必须可导出为文本、可进入版本库、可参与代码评审。图纸编辑器是差分的**生成器**，不是版本控制的替代品。任何只能在界面里点出来、无法导出为可评审文本的改动，都违反本章。

# 第三部分 运行与证据

## 12. 运行事件与持久性契约

静态拆解只能回答"有什么"，真实运行事件才能回答"发生了什么"。适配器既要输出静态结构，也要把平台原生消息、工具调用、审批、重试和产物事件归一化为 WGP Runtime Event。

v0.3 强制要求每个事件声明持久性等级。这是回放、审计与时间轴能否成立的前提。

| 等级 | 含义 | 允许的用途 |
|---|---|---|
| **durable** | 写入不可变日志，重载后仍可读 | 时间轴、回放、审计、评测证据 |
| **derived** | 不单独存储，但可由持久事件确定性重算 | 时间轴与聚合视图，必须标明重算函数 |
| **ephemeral** | 只在进程内存活一次的拦截点或钩子，重载后永久消失 | 仅实时高亮，必须标记为不可回放，**不得**用作审计或证据 |

**规则**

- 时间轴与回放只能建立在 durable 事件上。派生量必须可从同一批持久事件确定性重算。
- **任何进入模型请求的输入必须是 durable。** 否则回放会重建出一个与真实运行不同的会话，所有基于该回放的诊断结论都不可信。
- 事件负载默认引用而非复制敏感内容。日志、图纸与呈现层根据权限决定能否展开输入输出。
- 回放默认只复现视图，不重新执行具有外部副作用的工具。
- 事件格式必须携带版本号。读到未知事件类型时，实现必须要么拒绝解释该日志，要么依据事件自带的"可忽略"标记跳过；不得默认静默丢弃——静默跳过一个必需事件会重建出一个错误的会话。

事件示例：

```json
{
  "eventId": "evt_01J...",
  "runId": "run_20260826_001",
  "timestamp": "2026-08-26T09:28:31.221Z",
  "componentId": "tool.web.01",
  "type": "tool.completed",
  "status": "success",
  "durability": "durable",
  "durationMs": 842,
  "inputRef": "payload://sha256/...",
  "outputRef": "artifact://result/42"
}
```

平台原生的拦截点常常是 ephemeral：请求前钩子、工具执行包装器、流式转换器一类机制在内存中拦截并改写数据，但未必留下持久记录。适配器必须诚实标注，不得为了让时间轴"看起来完整"而把 ephemeral 事件伪装成 durable。

## 13. 可观测性与观测模式

可视化只有与真实运行轨迹、评测指标和组件版本绑定时，才构成可诊断的数字孪生。发光、变色、闪烁或阻塞不是装饰动画，而是对运行证据的实时编码。

| 视觉变量 | 默认含义 | 诊断解读 |
|---|---|---|
| 亮度 | 当前视图选中指标的水平 | 不与流量混用；含义随观测模式切换 |
| 颜色 | 健康状态 | 青蓝正常、黄色退化、红色失败、灰色离线 |
| 光流粗细 | 数据量或调用量 | 发现某条通路是否承担过高流量 |
| 粒子频率 | 吞吐量或调用频率 | 粒子密集表示事件更频繁 |
| 脉冲间隔 | 耗时与等待 | 长间隔或局部停滞提示高延迟或阻塞 |
| 闪烁与抖动 | 错误率或不稳定 | 持续闪烁提示重试、超时或输出波动 |
| 虚线 | 非当前运行的依赖关系 | 追踪环境、版本、能力或可选依赖 |
| 虚化轮廓 | 低保真度对象 | 该对象来自推断或标注，不可作为换件依据 |
| 锁扣与保护盒 | 权限、审批与沙箱边界 | 锁死、开启或黄色等待分别对应权限状态 |

为避免"一种光同时表示所有指标"造成误诊，图纸必须支持观测模式切换。任一时刻只有一种指标占用亮度通道。

| 观测模式 | 主要问题 | 高亮指标 |
|---|---|---|
| 活跃视图 | 现在哪些组件正在工作 | 调用状态、并发数、数据通路 |
| 质量视图 | 哪些组件正在拉低输出质量 | 任务得分、校验结果、贡献归因 |
| 性能视图 | 时间消耗在哪里 | 延迟、吞吐、重试、排队 |
| 成本视图 | 成本从哪些组件产生 | Token、API、计算、存储与网络成本 |
| 稳定视图 | 哪些组件容易失败 | 错误率、超时、方差、恢复时间 |
| 安全视图 | 能力边界和责任点在哪里 | 权限、密钥引用、审批、沙箱和副作用 |

## 14. 三级评测与双重评分

评测必须同时回答三个不同的问题，不能用一个笼统分数取代工程判断。

| 评测层级 | 评测对象 | 核心维度 |
|---|---|---|
| 零件评测 | 单个模型、工具、记忆组件或插件 | 准确性、延迟、成本、稳定性、安全性、可观测性、接口兼容 |
| 装配评测 | 组件间的接口、依赖、权限和数据流 | 依赖完整、契约匹配、数据效率、权限合理、容错、并行与瓶颈 |
| 整机评测 | 在真实或标准任务集中的完整智能体 | 任务完成率、输出质量、总成本、恢复能力、安全合规、长任务稳定性 |

综合分可用 `S = Σ(wᵢ × sᵢ)` 归一化聚合，但权重必须来自明确的 EvaluationProfile。安全审计机体与创意写作机体不应使用相同权重。界面必须同时保留多维分布、置信度、样本量与原始证据，而不是只显示一个 0 到 100 的数字。

> **双重分数** 一个零件应同时保留"本体性能分"与"当前机体贡献分"。高分模型若与上下文预算、工具契约或重试策略不匹配，在当前机体中仍可能是低贡献零件。这一区分是本方法论最具实践价值的度量：它解释了为什么榜单排名无法预测装机效果。

### 14.1 方差纪律

智能体输出的方差很大，单次或少量对照实验没有结论力。v0.3 把统计条件写入规范。

- ScoreCard 必须携带 `sampleSize` 与方差或置信区间；决策规则必须预先声明**最小可检测差异**。
- 未达到最小样本量的比较只能标记为"未定论"，不得进入版本历史，也不得触发自动换件建议。
- 禁止跨环境、跨任务集、跨保真度直接比较分数。

### 14.2 确定性重放：让贡献归因可测

换件类型不同，可用的实验设计也不同。这是把"贡献归因"从概念变为可测量的关键。

| 被换对象 | 推荐实验设计 | 方差水平 |
|---|---|---|
| 非模型零件（工具、记忆后端、压缩策略、权限、插件、调度参数） | **固定模型响应流**：使用录制的模型输出重放，只改被测零件 | 接近零，少量样本即可得到可信 delta |
| 模型零件（供应商、档位、推理配置） | 真实采样，固定任务集与环境，加大样本量 | 高，必须报告置信区间 |
| 提示词与上下文装配 | 真实采样，但可用同一批任务与固定随机种子降噪 | 中高 |

确定性重放的前提是平台能录制并回放模型流。具备该能力的 harness 可以把大部分非模型换件实验做成低成本的确定性回归测试，这是三级评测中最容易先落地的一块。

## 15. 诊断：定位到组件与边

诊断从整机症状出发，沿数据流、控制流与依赖回溯，逐层缩小到具体的组件或边，再给出可执行的修复差分。

| 问诊层级 | 核心问题 | 输出 |
|---|---|---|
| 症状 | 任务为什么失败、变慢、变贵或质量下降 | 受影响任务集、输出维度、时间区间 |
| 子图定位 | 问题集中在哪一组组件与边上 | 嫌疑子图（componentId 与 edgeId 集合） |
| 组件根因 | 是性能、配置、版本、插件还是输入数据异常 | 单件复测、参数检查、版本比对、替代件候选 |
| 边根因 | 接口、Schema、依赖、权限或数据传递是否失配 | 契约修复、增加适配器、补全依赖、申请权限 |
| 修复验证 | 换件或改装后是否真正提升 | 可执行 RecipeDiff + 同条件 A/B + 回滚路径 |

**定位的最小单位是 componentId、edgeId 或子图，不是器官。** 器官高亮是上述定位结果在呈现层的一种渲染方式，本身不构成诊断层级。这条规则的原因见第 17 章：多个语义不同的工程对象会映射到同一器官，若以器官为定位单位，诊断精度会在映射处丢失。

诊断建议只是假设，不是事实。每个建议必须附带证据链、预期影响、风险、回滚方法与验证计划。

## 16. 进化闭环

装配、运行、评测、诊断、换件、再验证构成闭环。一次改动只有满足全部下列条件，才可记入版本历史作为有效升级：

1. 相同任务集、相同环境、相同保真度等级；
2. 样本量达到预先声明的最小可检测差异要求；
3. 多维指标显示改善，且未在其他维度产生不可接受的退化；
4. 成本变化在可比范围内，或成本上升已被显式接受；
5. 未引入未经批准的权限扩大、副作用或沙箱放宽；
6. 携带可执行的反向差分。

不满足条件的改动可以保留为实验记录，但不得标记为升级。这条纪律的作用是防止"看起来变好了"沉淀为无法回溯的配置漂移。

# 第四部分 呈现层

## 17. 机体投影：人体认知映射

人形机体是一种**认知压缩界面**：用户不必先理解节点图、容器、依赖注入、上下文总线或调用栈，就能凭人体常识理解"大脑思考、感官输入、记忆保存、神经传递、手脚执行、装甲保护"。它在三个场景中价值明确——向非工程角色解释系统、新人上手、演示与传播。

**它的地位是呈现，不是定义。** 本章的映射不进入 ABIR 类型系统，不构成诊断层级，也不参与评测口径。

| 机体部位 | 默认语义 | 典型组件 |
|---|---|---|
| 大脑 | 理解、规划、决策 | 模型、模型路由、Planner、Validator |
| 眼睛与耳朵 | 感知与输入 | 文本解析、图像理解、语音、网页与消息接入 |
| 心脏 | 持续运行与调度动力 | Agent Runtime、Scheduler、Agent Loop |
| 脊柱与神经 | 上下文、事件和控制传递 | Context Bus、Event Bus、Message Router、Trace |
| 记忆器官 | 短期、长期与知识保存 | Session Store、Vector Store、Knowledge Base |
| 手臂 | 执行能力通道 | 浏览器、文件、代码、Shell、发布与设备控制 |
| 手掌与工具头 | 具体动作端点 | API、外部工具、CLI 命令、函数 |
| 关节 | 标准插槽与协议适配 | Port、Slot、Adapter、Schema Contract |
| 血液与能量流 | 数据和指标流动 | Payload、Stream、Metric、Artifact |
| 皮肤与装甲 | 权限、沙箱、审批与安全 | Permission Policy、Sandbox、SecretRef、Approval |
| 腿部与底盘 | 部署与运行环境 | 本地工作台、云环境、容器、远程服务器 |

**三条硬规则**

1. 一个器官在整个产品生命周期内保持一类语义。若"大脑"在一张图中表示模型、在另一张图中表示数据库，人体映射就失去了降低学习成本的价值。
2. 器官名不得出现在 ABIR 类型、事件类型、指标名或诊断层级中。
3. 点击器官必须能反向定位到图纸上的具体组件；图纸上的错误必须同步投射到器官视图。

### 17.1 映射的失效边界

诚实标注隐喻的失效处，比假装它普适更有工程价值。以下情形不存在唯一正确的器官归属：

- **上下文压缩**同时属于记忆管理、上下文装配与成本策略，没有单一器官。
- **沙箱、权限策略与人工审批**是三个语义完全不同的组件：沙箱规定技术边界，权限策略规定允许与拒绝，审批规定越界时由谁负责。三者全部塌到"装甲"会掩盖它们的区别，而这个区别恰恰是安全审计最需要看清的。
- **子智能体**是拥有自己会话、工具集与运行循环的**完整机体**，是递归嵌套的机器，不是多长出来的手臂。强行画成手臂会与递归组合原则冲突。
- **事件总线与调度器**的区别在人体中没有自然对应物，"神经"与"心脏"的划分是约定而非直觉。
- **模型路由与降级策略**是决策而非器官，画成"第二个大脑"会暗示不存在的并行推理。

处置规则：遇到映射冲突时以工程结构为准。允许该对象在机体视图中显示为通用模块、聚合进最近的容器，或不显示。**不允许**为了让机体图完整而伪造一个器官归属。

通用人形是默认教学视图。多大脑、多手臂、多记忆核心等形态用于表现多模型协作、多工具并行或多运行时，属于视觉聚合手段，不代表底层计算结构。

## 18. 三维机体投影

三维视图用于展示、巡检、传播与局部导航。它读取 ABIR 与 visualBinding，不保存独立的逻辑关系。

三维必须采用分层细节：五百个逻辑组件不应生成五百条手臂；远距离只显示大模块，爆炸拆解或放大后才揭示内部组件。点击三维部位应反向定位二维图纸；二维的错误与低保真度标记也应同步投射到三维。

三维是路线图的最后阶段（第 22 章 P5）。在结构准确性、事件持久性与评测证据尚未成立之前投入三维，会产出一个无法用于工程判断的演示品。

## 20. 安全、权限与治理

结构可见性的提升会同时放大风险暴露：密钥、内部路径、提示词、数据样本与操作权限都可能因为"画出来"而更易获取。安全必须进入组件协议、关系模型与运行事件，而不是作为后置功能。

**基础要求**

- 凭据只以 SecretRef 或锁定组件出现，画布不显示明文。
- 权限关系必须区分允许、拒绝、需要审批和继承范围。
- 沙箱与审批是不同组件：沙箱规定技术边界，审批决定越界时由谁确认。
- Trace 默认记录结构化摘要和内容引用，敏感负载按权限展开。
- 运行回放默认不重新调用具有外部副作用的工具。
- 适配器必须遵守平台条款和用户授权，不逆向采集未公开推理内容。
- 组件市场中的第三方模块必须声明权限、网络、文件和数据使用范围；差分必须显示它引入的每一项新权限。

**图纸作为特权产物**

一份标注了全部组件、权限关系、沙箱边界与审批点的完整机体图，等价于一份攻击面地图。它是本方法论产出的最敏感资产。

- 完整结构加权限视图默认按角色授权，不随会话产物一并导出。
- 对外分享必须支持脱敏投影：隐去权限关系、凭据引用、内部路径与沙箱细节。
- 差分与诊断报告在跨组织传递前必须走同一套脱敏路径。

**自读禁令**

具备自我修改能力的智能体**默认不得读取自己的 ABIR 与权限图**。把一份自身约束地图交给可被提示注入影响的模型，等于把绕过约束所需的全部信息一并提供。若确有需要（例如自动化运维场景），必须作为显式挂载的独立能力，受审批与完整审计约束，并在差分中标记为权限扩大。

这一条有成熟先例：具备"让模型检查并挂载自身插件"能力的 harness，会把该能力实现出来但**默认不纳入发布配置**，需要使用者显式挂载。本规范把这一实践固化为要求。

> **治理目标** 让用户看到智能体拥有什么能力、能力连接到哪里、正在使用什么权限，以及哪个动作需要人类负责——同时不让这份地图成为新的攻击入口。

## 21. 首个参考实现：DSH

DSH（DeepSeek Harness）不是本方法论的概念所有者，而是其首个参考实现与验证平台。

选择它作为起点的理由是技术性的，不是署名关系：**在主流参考对象中，DSH 是结构本身已经是一等、机器可读、且被持续集成校验新鲜度的产物的那一个。** 因此它的拆解可以直接达到 F3 声明级，而其他平台起步通常在 F1/F2（第 8 章）。这把第一阶段的工作从"逆向推断一个黑盒"变成"投影一张已经存在的强类型图"，难度不在同一量级。

### 21.1 使 ABIR 可实现的五个事实

**一、一切皆插件的插件树。** 模型适配器、工具注册表、会话日志、乃至 agent 主循环本身都是插件，挂在同一个共享上下文上；所有注册都是可回滚的效果（effect），插件卸载时自动撤销。这意味着 ComponentInstance 与运行实体是一一对应关系，而不是近似聚合。

**二、profile / bundle 的分层 patch 组合。** 一个运行中的实例，其插件树由有序层叠加而成：先是各 bundle 按声明顺序，然后是用户 patch 层，最后是命令行覆盖层。每一行按 id 可被上层整体替换。**这就是 AssemblyRecipe 的原生格式**，而"换件"天然表达为增加一个 patch 层——不需要发明新的编译目标（第 11 章的 Compiler 在此几乎是恒等映射）。

**三、配置可打印。** 平台提供命令直接输出实际启动的整棵树（`--dump-config`）。这是 F3 保真度的直接来源：组件实例、其配置字段、其在树中的位置，全部是可解析文本而非推断结果。

**四、持久事件与仅实时拦截点在平台层就是分开的。** DSH 的会话日志是 append-only 的持久事件流，并有运行时断言保证"任何进入模型请求的内容都必须能从日志重建"。更关键的是，它的**持久事件类型清单是由脚本生成、并被持续集成校验新鲜度的产物**（本文写作时为 48 个类型）；而请求前拦截、工具执行包装、流式转换等扩展点属于仅实时机制，不在该清单内。这意味着第 12 章的持久性契约不需要适配器去猜——平台自己已经做出了这个区分，适配器只需转录。

**五、能力接缝与生成目录。** 平台要求每个可替换能力由"服务定义 / 服务提供者 / 消费者"三个角色共同构成，并生成一批机器可读目录：模块依赖图、工具清单、配置字段清单、持久化清单、事件生产者与消费者对照表。这些正是 ComponentDefinition 的端口、能力、边与权限关系的现成来源。

### 21.2 三项额外便利

- **热重载与效果回滚**：平台内建热重载，且注册即效果、卸载即撤销。这使"在图纸上拖走一个组件、运行中的智能体不重启完成重新装配"在原理上可行，是本方法论最具说服力的演示形态。
- **现成的观测出口**：平台提供 JSON-RPC 形式的运行时 SDK 与宿主侧事件推送，适配器可以在不侵入内核的前提下订阅事件流。
- **现成的确定性重放设施**：平台自带录制与重放模型流的测试支持能力，可直接用于第 14.2 节的低方差贡献归因。

### 21.3 版本锚定

DSH 处于 developer preview 阶段，明确声明会有破坏性变更，并在 pre-release 期间优先修正基础设计而非维持兼容（本文写作时最新发布标签为 `dsh-v0.1.1-rc.2`）。因此：

- 适配器必须 pin 具体版本，不得依赖"最新"。
- 每一份 BenchmarkRun 的环境记录必须包含被测 harness 的精确版本与配方版本。
- 规范与适配器分离演进：ABIR 的语义不随单一平台改名而变动。

## 22. 分阶段实施路线

### P0 规范固定

交付 ABIR、保真度分级、持久性契约、差分与风险标记、评测证据与诊断报告最小字段。通过条件：一台 DSH 智能体可被完整映射为 F3 结构，且每个对象的来源可核对。

### P1 一条纵切（决定性阶段）

不要先铺开多个功能房间。信息量最大的第一刀是一条端到端纵切：

1. 从 DSH 的配置输出生成 F3 级 ABIR；
2. 用服务注入声明与生成目录补出强类型边；
3. 渲染二维图纸，只实现解构模式与运行模式；
4. 订阅持久会话事件，实时点亮组件与数据通路；
5. 执行**一次**换件：生成一个 patch 层，观察热重载真实生效；
6. 用同一任务集跑一次 A/B，非模型零件采用固定模型流以压低方差，产出携带证据引用的 ScoreCard；
7. 自动指出一个薄弱组件，给出可执行的 RecipeDiff 与反向差分。

**通过条件**：图纸上的一次改动真实改变了运行行为，且改动前后的差异有可复现的证据。

### P2 观测完整化

时间轴、无副作用回放、六种观测模式、错误传播、诊断定位到边。通过条件：所有视觉编码都能追溯到具体事件或指标，且回放只使用 durable 事件。

### P3 评测体系化

Test Bench、Scoring Engine、方差纪律、双重评分、贡献归因。通过条件：任一分数可下钻到任务集、样本量、方差与原始证据。

### P4 跨平台扩展

先建立 F1/F2 观测级适配器，明确标注保真度差异，不越级提供换件能力。通过条件：同图比较时双方保真度可见，且不产生跨等级的直接分数比较。

### P5 机体投影

人体视图与三维机体，只读同一份结构事实，支持双向定位。通过条件：不产生第二份结构事实。

### P6 生态化

规范、SDK、一致性验证器、零件与插件市场、评测榜单。通过条件：第三方可实现通过验证器的兼容组件。

> **判据** P0 与 P1 决定概念是否成立。若二维结构不能准确影响真实运行，任何机甲动画都只是视觉演示。三维不能补救结构的不准确。

## 23. 价值、边界与开放问题

### 23.1 价值

核心价值是把智能体配置从附属设置提升为有差分、有测试、有归因的工程对象，从而降低复杂智能体的理解、验证与治理成本。

| 价值方向 | 体现 |
|---|---|
| 理解与解释 | 把抽象架构转化为逐层显形、标注保真度的二维图纸 |
| 变更与治理 | 语义差分、风险标记、审批责任与可靠回滚 |
| 测试与比较 | 零件、装配、整机在同一评测框架下可重现地比较 |
| 归因与升级 | 从整机症状定位到具体组件与边，用受控实验验证换件效果 |
| 跨平台迁移 | 通过 ABIR 在标注保真度的前提下比较与转换不同智能体结构 |
| 运行与调试 | 把持久事件映射回组件、关系与时间轴 |
| 安全与审计 | 让权限、沙箱、审批和副作用成为可见且可差分的结构 |
| 沟通与传播 | 用受约束的机体投影向非工程角色解释能力形态 |

潜在使用者包括智能体开发者、企业 AI 平台负责人、安全审计人员、教学培训人员，以及需要为智能体行为负责的业务管理者。

### 23.2 边界

- 本方法论不评价模型本身的能力上限，只评价装配与配置带来的差异。
- 它不能把 F1 观测级结构提升为可编辑事实；提升保真度依赖平台开放程度，不依赖工具努力程度。
- 它不承诺替代人工工程判断，只承诺让判断建立在可追溯证据上。
- 呈现层的美观程度不构成成功指标。

### 23.3 开放问题

- **贡献归因的因果准确性**：确定性重放能覆盖非模型零件，模型零件的归因仍受高方差限制。
- **跨平台事件语义损失**：不同平台的拦截点与持久事件划分不同，归一化过程中的信息损失需要量化。
- **任务集代表性**：标准任务集能否代表使用者的真实目标，是全部评分结论的前提假设。
- **复杂图的布局稳定性**：大型配方在增量改动后保持可读且位置稳定，仍是待验证的工程问题。
- **组件版本兼容**：端口与契约的兼容范围如何表达与校验。
- **动态生成工具的生命周期**：运行期临时产生的能力如何进入结构与评测。
- **成本与质量的可比性**：不同定价与延迟结构之间的折算方法。
- **敏感 Trace 的治理**：证据保留期限、脱敏粒度与审计要求的平衡。
- **开放标准的演进机制**：规范如何在多实现存在时保持一致。

> **评价标准** 本方法论的成功不以"机器人看起来多酷"衡量，而以六条为准：结构是否准确并标注了来源、视觉是否来自真实且分级的事件、分数是否有样本量与证据、诊断是否指向具体组件与边、换件是否能被受控实验验证、跨平台比较是否在合法保真度范围内。

## 附录 B 运行事件字典与持久性分级（v0.3）

规范事件类型及其**要求的最低持久性**。适配器可以提供更强的持久性，不得提供更弱的。

| 事件类型 | 含义 | 最低持久性 |
|---|---|---|
| task.created | 任务创建 | durable |
| task.updated | 计划或状态更新 | durable |
| session.started | 会话开始 | durable |
| session.paused / resumed | 会话暂停与恢复 | durable |
| instruction.loaded | 指令加载 | durable |
| context.loaded | 上下文加载 | durable |
| context.compacted | 上下文压缩 | durable |
| memory.recalled | 记忆检索 | durable |
| memory.updated | 记忆写入 | durable |
| model.requested | 模型请求（含最终入参来源） | durable |
| model.completed | 模型响应完成 | durable |
| tool.requested | 工具调用请求 | durable |
| approval.requested / resolved | 审批请求与结果 | durable |
| tool.started | 工具开始执行 | derived |
| tool.completed / failed | 工具执行结果 | durable |
| subagent.started / completed | 子智能体生命周期 | durable |
| artifact.created | 产物生成 | durable |
| verification.failed | 验证失败 | durable |
| retry.started | 重试开始 | durable |
| run.completed / failed / cancelled | 运行终止 | durable |
| metric.observed | 指标写入证据库 | durable |
| evaluation.started / completed | 评测生命周期 | durable |
| part.degraded | 零件进入退化状态 | derived |
| diagnosis.created | 生成带证据的诊断结论 | durable |
| replacement.proposed | 生成换件或改装建议 | durable |
| experiment.compared | 完成基线与改装方案对比 | durable |
| intercept.pre_request | 请求前拦截点触发 | ephemeral |
| intercept.tool_wrap | 工具执行包装器触发 | ephemeral |
| intercept.stream_transform | 流式转换器触发 | ephemeral |

**映射示例：DSH 事件到规范事件**

DSH 的持久事件类型清单由脚本生成并被持续集成校验，可直接作为映射的左侧输入；其扩展点（请求前拦截、工具执行包装、流式转换等）不在该清单内，映射为 ephemeral。

| DSH 事件 | 规范事件 | 持久性 |
|---|---|---|
| `turn/start`、`turn/end` | task.created / run.completed | durable |
| `step/start`、`step/end` | model.requested 边界 | durable |
| `user/message` | input.message | durable |
| `request/header`、`request/context` | model.requested | durable |
| `assistant/chunk`、`assistant/message` | model.completed | durable |
| `tool/call`、`tool/result` | tool.requested / tool.completed | durable |
| `approval/asked`、`approval/decided` | approval.requested / resolved | durable |
| `compaction/start`、`compaction/summary`、`compaction/prune` | context.compacted | durable |
| `llm/retry`、`llm/retry-started` | retry.started | durable |
| `subagent/descriptor` | subagent.started | durable |
| `agent/pre-step`、`agent/request`、`llm/stream`、`tools/execute` | intercept.* | **ephemeral** |

最后一行是持久性契约存在的理由：这些是功能强大的拦截点，可以改写送入模型的内容，但它们本身不留持久记录。把它们当作可回放事件会构造出一个与真实运行不同的历史。

## 附录 C 评测与诊断报告最小字段

| 对象 | 必要字段 | 目的 |
|---|---|---|
| EvaluationProfile | id、taskType、metricWeights、constraints、passRules、**minDetectableEffect** | 规定什么叫"更好" |
| BenchmarkRun | runId、recipeVersion、**harnessVersion**、environment、dataset、seed、**fixtureRef**、traceRef | 保证测试可复现 |
| ScoreCard | level、dimensionScores、aggregate、**sampleSize**、**variance**、confidence、**fidelity**、evidenceRefs | 保留多维得分与统计条件 |
| Contribution | componentId、baseline、delta、method、**designType**、uncertainty | 估计零件在当前机体中的贡献 |
| Diagnosis | symptom、suspectComponents、suspectEdges、rootCause、evidence、actions、risk、**rollback** | 从症状形成可行动建议 |
| ExperimentComparison | control、variant、sameConditions、deltas、**sampleSize**、decision、rollback | 判断换件是否构成有效升级 |

`designType` 取值：`real-sampling`（真实采样）、`fixed-model-stream`（固定模型流）、`fixed-seed`（固定种子）。它决定该 delta 的方差水平与可信区间算法。

## 附录 D 一致性判定：什么才算一个 WGP-ABF 实现

以下八条构成可验证的最低合规清单。

1. 每个结构对象携带 `source` 与 `fidelity`，且 F1/F0 对象在视图中与 F3/F2 明显可区分。
2. 每个运行事件携带 `durability`；时间轴与回放只使用 durable 与 derived 事件。
3. 图纸上的一次结构改动能生成语义差分，并**真实改变运行行为**。
4. 每个分数可下钻到 EvaluationProfile、样本量、方差与原始证据引用。
5. 每个诊断结论指向具体 componentId 或 edgeId，并附可执行修复与反向差分。
6. 具有副作用、成本显著或权限扩大的变更需要人工批准，且批准记录与差分绑定。
7. 机体视图与三维视图不保存独立业务结构，且能反向定位到图纸对象。
8. 完整结构加权限视图默认不对被诊断的智能体本身开放。

未满足第 1 至 6 条的实现，只能称为可视化演示，不得称为 WGP-ABF 实现。
